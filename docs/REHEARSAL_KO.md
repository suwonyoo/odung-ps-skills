# 실제 사용과 가상 시나리오

## 사용자가 할 일

공개 준비 저장소를 복제하고 별도 작업 폴더에 설치한다. 특정 행사 이름을 말하거나 단계마다 스킬을 호출할 필요는 없다. 평가 환경에 파일을 들여오는 방법과 허용 범위는 실제 안내를 따른다. 설치는 의존 패키지를 다운로드하지 않는다.

```bash
git clone --branch v3.1.0 https://github.com/suwonyoo/odung-ps-skills.git
mkdir task-workspace
python3 odung-ps-skills/scripts/install.py --target "$PWD/task-workspace" --apply
cd task-workspace
```

문제 자료를 실제 제공 위치에 두고 Codex에 말한다:

> 문제 파일은 inputs/brief.pdf, 데이터는 data/야. 원하는 결과는 배정표 생성·저장과 조회 화면이고 상세 조건은 안내문에 있어. 작업 시간은 180분이야. 담당자에게는 내가 직접 질문하고 답변을 붙여 줄게. 시작하자.

자동 선택이 안 되면 한 번만 `.agents/skills/task-start/SKILL.md를 읽고 시작해 줘`라고 덧붙인다. 기존 AGENTS.md는 설치기가 바꾸지 않는다. 레포를 연결하는 행위 자체가 코드를 실행하지는 않는다.

v3.1의 일반 작업 진입점은 `task-start`이며 단계 지침은 `task-intake/build/verify/finish`다. 이전 이름을 쓰던 진행 중 폴더는 그대로 마무리하고 다음 과제부터 새 폴더에 설치한다. 시간을 생략하면 180분을 임시 예산으로 표시한다. 일반 개발에 AI 허용 선언을 요구하지 않으며, 평가에 해당할 때만 실제 AI 사용 규칙을 확인한다.

사용자는 파일·시간·실제 규정을 알려 주고, 중요한 선택에 답하고, HR 질문을 전달하고, 필요한 UI 확인과 공식 제출을 한다. task/intake JSON, 단계 이벤트와 문서 갱신은 에이전트가 담당하도록 지침을 넣었다.

상태판을 다른 터미널에 띄우고 싶으면 `python3 .harness/flow.py status --watch`. 재개할 때는 “기존 상태로 계속하자”면 된다. 시계는 초기화되지 않는다. 제한시간을 임의로 늘리는 명령은 없다.

## 디렉터리

| 위치 | 내용과 책임 |

| task-workspace/ 또는 제공 프로젝트 | 실제 구현·제출 경로. 기존 프로젝트 구조가 우선 |

실제 평가가 요구하는 문서는 안내된 제출 위치에 별도로 만든다. 내부 숨김 폴더가 자동 제출된다고 가정하지 않는다. 모든 명령은 과제 루트에서 실행한다. 다른 위치에서는 `--project ABSOLUTE_PATH`를 사용한다.

## 180분 가상 진행

다음은 성능 예측이 아니라 **시간 배분안**이다. HR 응답시간, 자료 규모, 설치 제약과 모델 난이도에 따라 달라진다. 전체 180분에 HR 대기와 실패 복구도 포함된다.

가상 과제: 교육 요청을 교육실에 배정하고, 인원을 이동편에 실어 나르며, 운영자가 만든 계획을 직원이 조회한다. 방 수용량·장비·인원 중복·차량 정원·이동시간·데이터 revision이 연결된다.

| 경과 | 단계 | 실제로 하는 일 | 이때 남는 것 |
|---|---|---|---|
| 0–5분 | intake | 실행환경·제출·원문 파일 확인 | 자료 목록, 실제 예산, 제출 조건 |
| 5–20분 | intake | 키/join/단위/결측, 하위 결정과 공유 자원 분석, 우선 HR 질문 | intake/task, 질문 Q1–Q3, 최초 동작 경로 |
| 20–35분 | modeling | 답변 반영, 한 솔버 선택, 작은 가능/불가능 모델 실측 | 모델 명세, 선택 비용, 계약 v1 |
| 35–60분 | build | 작은 입력→배정→독립 검증→저장→조회 최초 연결 | 눈으로 확인 가능한 첫 실제 결과 |
| 60–100분 | build/integrate | 코어 규칙과 연결 구현을 분리, 대표 크기 데이터 조기 실행 | 실제 품질·시간, 규칙 누락 수정 |
| 100–130분 | integrate | HR 후속 답변·비대칭 이동·데이터 교체·실패 처리 | 필요하면 모델/계약 v2, 이전 증거 만료 |
| 130–160분 | verify | 경계·불가능·타임아웃·오래된 후보·누락 검사 | 현재 소스의 근거, 한계 |
| 160–180분 | finish | 기능 동결, 제출 파일·실행 문서·협업 기록·수동 확인 | 정확한 인계와 사용자 제출 |

실제 210분이 주어지면 추가 30분을 대표 데이터 검증·복구 여유에 우선 배정한다. 마지막에 새 프레임워크나 두 번째 솔버를 넣지 않는다. 그 후 AI 금지 평가가 있으면 모든 도움을 중단한다.

예: 82분에 “한 요청의 people=9가 한 교육집단인지 분할 가능한 인원인지”가 모호해졌다. 코어·이동편 세션을 질문 Q4에 묶고 단계 진행을 잠근다. 사용자에게 짧은 DM 문장을 준다. 답을 기다리는 동안 독립적인 조회 오류 표시를 진행할 수 있다. 답변 후 원문을 저장하고, 분할 허용이면 변수·검사·계약을 수정하여 modeling으로 돌아간다. 기존 pass를 다시 사용하지 않고 필요한 검사를 재실행한다.

## 위기 대응

| 상황 | 즉시 행동 | 포기하면 안 되는 것 |
|---|---|---|
| HR가 늦거나 답이 상충 | 관련 작업 중단, 독립 작업 진행, 원문 대조 후 최소 후속 질문 | 답을 만들어내기/필수 제약 임의 완화 |
| 데이터 join 후 행이 줄어듦 | 미매칭 키·중복 정책 확인, 오류/보류를 명시 | 조용한 누락을 성공으로 처리 |
| JDK/패키지 설치 불가 | 사전 준비한 다른 실행 경로 검토; 작은 검증된 baseline 또는 blocker 공개 | 미실행 솔버를 작동한다고 기록 |
| UNKNOWN/시간 초과 | incumbent와 독립 검증 확인, 입력·검색 공간 축소 검토 | 불가능 증명 또는 최적해라고 말하기 |
| 후보가 hard 규칙 위반 | 발행하지 않음. 유효한 이전/기준 계획만 fallback 가능 | 실패한 후보를 최종 결과로 둔갑 |
| 후보 생성 중 입력 변경 | 해당 입력 snapshot/revision 재대조, 오래된 후보 격리 | 새 데이터의 계획으로 발행 |
| 터미널/에이전트 중단 | status와 로그 확인, 관찰 가능한 죽은 실행만 복구 | 원래 종료 결과를 추측 |
| 병렬 수정 충돌 | 공동 파일 단일 소유자, 작은 변경 단위 통합 | 디렉터리 전체 덮어쓰기 |
| 종료 30분 전 | 기능 동결, 현재 요구·검사·문서 일치 확인 | 겉보기 완료를 위해 실패 근거 삭제 |

이 중 버전 대조·원자적 발행·fallback은 실제 서비스에 구현하고 검사할 **요구 패턴**이다. 이 준비 도구가 모든 서비스의 데이터베이스 트랜잭션을 제공하는 것은 아니다.

## 약점과 보완

1. 에이전트의 의미 이해가 병목이다. intake 검사는 빈칸/관계/변경만 잡는다. 가장 중요한 제약 두세 개는 사용자가 작은 예시로 이해를 확인한다.
2. 질문을 너무 많이 하면 시간이 줄어든다. 필수 의미와 목표 우선순위부터 묻고, 되돌릴 수 있는 선택은 AI 기본값으로 기록한다.
3. 명세·하네스도 비용이다. 모든 파일을 장문으로 채우지 않고, 실제 선택이 생겼을 때 짧게 갱신한다. 검증용 스크립트를 쓰는 시간도 예산에 넣는다.
4. 현재 솔버 예제는 작은 직원 배정만 구현했다. 실제 경로 최적화·교육 배정·정류장 선정 등을 자동 모델링하는 범용 엔진이 아니다.
5. 공개 레포와 로컬 테스트는 시험 클라이언트 호환성을 증명하지 않는다. 시험 전에 같은 시작 문장으로 설치·실행·수동 질문·재개를 한 번 연습한다.
6. 전체 입력/문서 변경에 보수적으로 증거가 만료될 수 있다. 다시 실행할 수 있는 빠른 검사와 오래 걸리는 검사를 분리하되 필요한 검증을 건너뛰지 않는다.
7. 기록은 파일이며 위변조 방지 증명이나 강제 샌드박스가 아니다. 다른 터미널의 직접 명령, 규칙을 무시한 AI, 외부 세션까지 차단하지 못한다.
8. 절대적인 '완벽'이나 합격률은 측정하지 않았다. 합성 시나리오 통과와 실제 평가 성과는 구별한다.

## 이번 준비 환경에서 측정한 값

2026-11-04, Linux/Python 3.12, OR-Tools 9.15.6755, Timefold CE 2.7.1/Java 21.0.13. 각 1회, 같은 작은 직원 배정 예제, 내부 solve 제한 0.5초다. 시작·입력·solve·결과 저장을 포함한 프로세스 시간이다. 환경·런타임 초기화·알고리즘이 달라 솔버 성능 순위를 뜻하지 않는다.

| 경우 | OR-Tools | Timefold |
|---|---:|---:|
| feasible 정상 계획 | 0.476초 | 1.331초 |
| impossible 입력 | 0.494초 | 0.892초 |
| day 필드 누락 거부 | 0.447초 | 0.250초 |
| 소수 day 거부 | 0.315초 | 0.267초 |

같은 환경의 JDK 다운로드·압축 해제는 22.83초, Maven 다운로드·압축 해제는 7.16초, 최초 의존성 취득 포함 Java 빌드는 36.64초였다. 실제 시험망에서는 훨씬 오래 걸리거나 불가능할 수 있다. 이 값들을 시험 예상시간으로 사용하지 말고, 시험 전 실행 가능성을 확인하고 실측을 새로 남긴다.
