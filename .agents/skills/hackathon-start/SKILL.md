---
name: hackathon-start
description: Start or resume an AI-permitted hackathon when the user supplies problem files, desired results, and says to start or continue. Coordinate rigorous intake, solver selection, phase display, manual HR questions at any phase, timed work, parallel ownership and evidence-backed notes without requiring separate skill commands. Stop for an active no-AI assessment.
---

Read actual project instructions and supplied files. Preserve their stack, submission paths and permitted models. Use only in preparation or an AI-permitted work phase; stop for an active no-AI assessment.

1. Locate the task workspace. If inside the public kit, follow its AGENTS.md to install into a separate task directory; never place real task files in the public preparation checkout. If `.harness/flow.py` is absent and the kit is unavailable, state the missing setup and follow the procedure in text without inventing tool execution.
2. Read `.harness/WORKFLOW_KO.md`. Run `python3 .harness/flow.py start --minutes N` with the actual allowed duration. If unknown, explicitly use a provisional 180-minute budget. Start is idempotent: preserve the original deadline and closed state. Read current STATUS.md, workflow.json and the indicated `.agents/skills/NAME/SKILL.md` instead of restarting.
3. Follow routes without asking the user to invoke every skill: intake → modeling → parallel-build → integrate → verify → finish. Run `event inputs-reviewed`, `contract-ready`, `candidate-ready`, `integrated`, `verified` only when their actual conditions hold. An event command records a transition; it does not execute a skill or launch an agent. Never skip the intake or verification gate to make a board green.
4. **At every boundary, failure, new file, changed rule and integration discrepancy**, ask whether an unknown changes data meaning, a hard constraint, objective order or acceptance. If so, read stakeholder-bridge, record a question and pause dependent work immediately, regardless of the phase. A new dependency can appear after initial intake. Do not wait until final review.
5. Present at most three ready-to-answer questions whose prerequisites are settled. Give the user exact DM text and why it matters. Required unanswered decisions stay pending; silence/time passing is not consent. A reversible implementation default can be chosen by AI and recorded as such. Ask material user choices as: decision → term + easy meaning → options/cost → recommendation → check.
6. After a real copied reply, use question answer/resolve and resume. A material change requires new intake review, model/contract/check updates and fresh evidence. Do not treat the reply itself as implementation or verification. Inspect the actual files and remaining blockers on resumption.
7. At each significant update show: `[phase i/6 | session/task | remaining budget]`, what changed, blocker and next step. Use worker at task start/change/end and run around costly commands. Display measured duration and configured limits, never a guessed optimality ETA or percent-complete. Manual session elapsed time is wall time, not continuous activity.
8. Establish the first complete input→decision→validation→output slice before decorative UI. Define one concrete I/O/failure contract and owner. Assign disjoint paths; one writer owns dependencies/shared types. Parallel agents require user/project authorization and environment support. Multiple terminals do not automatically create parallel model workers. Never merge by overwriting whole directories.
9. Keep concise working records as decisions occur: intake.json, model-spec.md, architecture.md, decisions.md, GLOSSARY.md, AI_collaboration.md and limits.md. Read references/working-records.md. Attribute proposals, AI defaults, real user choices and real checks separately; do not invent a retrospective story.
10. With 30 minutes remaining, stop optional features and new solver/stack switches; integrate, verify and prepare exact deliverables. Use the actual task deadline, not this default, for AI phase cutoff. A closed runner does not terminate other sessions. Never send HR messages or submit the assessment automatically.

Recovery: use status after interruption; preserve failed evidence. Dead-lock/run recovery commands require observed dead local processes. Do not remove a live lock, turn UNKNOWN into INFEASIBLE, relax hard rules or publish an invalid fallback under time pressure. The harness checks structure and recorded evidence; the agent/user still own semantic correctness.
