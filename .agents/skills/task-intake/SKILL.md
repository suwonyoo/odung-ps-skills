---
name: task-intake
description: Analyze supplied problem files and data before structured implementation, especially a new brief or material rule change in this task workflow. Identify combined subproblems, shared constraints, unknown business rules, exact outputs and independent acceptance checks. No competition context is required. Respect an actual no-AI assessment restriction.
---

Read actual task instructions, relevant files and the supplied project before proposing a solution. Preserve exact delivery paths, stack and evaluation constraints. Read `references/intake-framework.md`; it defines the compact analysis and intake.json fields. If installed, read `.harness/START_HERE_KO.md` for the strict task.json schema.

Analyze in small passes and publish findings as they become useful: goal/output, then data/rules, then coupled decisions/unknowns, then proposed model and first slice. Do not wait for intake.json or the full analysis to be complete before explaining anything. Label partial coverage and assumptions; cite the actual source location. After the first pass, give the user one useful optional review (such as checking the goal against the rubric), and route any necessary business decision or manual DM immediately while independent analysis continues. The intake budget is work time, not a silent waiting period.

1. Inventory supplied files, their roles and precise locators (section/page/table). Read decision-bearing content, including tables; mark unreadable/missing material as unknown. Record real sources, not remembered examples. Capture user-provided brief text in the separate task workspace when it has no file.
2. Restate the observable goal, users, required outputs and what counts as failure. Separate required behavior from optional polish. Build task.json with actual requirement IDs, deliverable paths and behavior-checking commands/manual checks. Unknown submission requirements are questions, not guessed filenames.
3. Inspect data before selecting a solver: IDs, join cardinalities, units/scaling, dates/timezones/interval boundaries, missing and duplicate policy, availability/directionality, row counts and candidate variable growth. Distinguish facts observed by a command from assumptions. A clean parse does not prove data meaning.
4. Decompose mixed tasks into decisions and service responsibilities. For each component record input/output, requirement IDs and execution dependencies. Explicitly map shared capacity, demand, time, identity and version constraints. Cyclic decisions need a joint model, bounded feedback or a stated approximation; never pretend independently optimal stages yield a globally feasible/optimal plan.
5. Write sourced hard/soft/behavior rules and link each to observable checks. For each rule expose scope/quantifier (every person vs average), units, inclusive boundaries, exceptions and a tiny expected result plus a boundary/counterexample; an authoritative exact statement can settle these without DM. Determine objective order before adding weights; do not invent a threshold for “as much as possible.” Identify conflicting sources and coupling losses. Draft one feasible baseline and one smallest end-to-end slice. Estimate model size and a reduction strategy; do not spend the entire analysis budget solving the algorithm.
6. Review ambiguity and contradiction before any task-model solver run, and again whenever relevant inputs or rules change. List consequential unknowns even if HR cannot answer them yet. Use stakeholder-bridge at this or any later phase. Respect contact mode; no-DM means documents or necessary user decisions without an external-message loop. Ask at most three ready questions, one decision each. A vague/partial reply stays unresolved: preserve confirmed clauses and ask a concrete distinguishing case about the remainder. Explicitly pause dependent tasks; independent inventory, required design or adapter scaffolding may continue under recorded ownership. Do not invent answers, factual thresholds or soft exceptions to a mandatory rule.
7. Fill `.harness/work/intake.json` with the framework's fields; blank, generic example and unsupported factual claims are not a completed analysis. Use explicit not-applicable with a reason where appropriate. Complete task.json checks before emitting `event inputs-reviewed`. The command validates references, coverage, dependency cycles and source hashes, not whether your interpretation is true.
8. Briefly show the actual problem structure, most consequential tradeoff, current questions and first runnable slice. Estimate the remaining work from file/data volume, unknowns, environment readiness, required interface/design and model size; do not start from fixed phase percentages. Use low/high ranges, actual session capacity, dependencies, contingency and protected verification/handoff. Revise a flexible target after the first pass; preserve a real fixed deadline and disclose scope conflicts. Route to solver-modeling while independent work continues when dependent decisions wait.

Keep ordinary engineering records, with technical terms explained in plain language. Do not build answer scripts for an active no-AI assessment, transmit forbidden files, automate HR chat, alter platform permissions or replace the supplied project with a generic solution.
