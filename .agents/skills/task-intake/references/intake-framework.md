# 첫 분석: 문제를 실행 가능한 명세로 바꾸기

첫 자료 확인 뒤 시간 계획을 세우고, 데이터·질문·모델 규모를 확인하며 갱신한다. 180분 작업의 분석 15–25분은 초기 예산 예시이며 고정 일정이나 완료시간 보장이 아니다. AI가 자료를 읽고 아래 파일을 채운다. 사용자는 업무 판단과 수동 HR 답변에 집중한다.

## 8가지 관점

| 관점 | 확인할 것 | 흔한 함정 |
|---|---|---|
| 결과 | 누가 어떤 입력으로 무엇을 얻나; 필수 파일·시연·실행 명령 | 화면은 있지만 핵심 계산 없음 |
| 근거 | 원문 파일/쪽/항목, 사용자 전달 답변, AI 가정 구분 | 댓글이나 예제를 시험 요구사항으로 사용 |
| 데이터 | 키 유일성, join 1:1/1:N, 단위, 시간대, 경계, 누락·중복 | inner join으로 미매칭 인원을 누락 |
| 결정 | 선정/경로/배차/조회 등 구별, 각 입력·출력 | 모든 문제를 하나의 솔버 예제에 억지로 삽입 |
| 연결 | 공유 자원·시간·수요, 단계 간 실행 가능성 | 단계별 최적이면 전체도 최적이라고 주장 |
| 규칙·목표 | 절대 금지 vs 선호, 악화 금지, 우선순위 | 임의 가중치로 중요한 규칙을 상쇄 |
| 규모·한계 | 변수·간선 수, 후보 축소, 분해 손실 | 전체 규모를 마지막에 처음 실행 |
| 검사 | 손계산 사례, 불가능/누락/경계/변경 입력, 발행 실패 | exit 0을 규칙 충족으로 간주 |

결측이 '미근무'인지 '입력 오류'인지는 다른 문제다. 비대칭 이동시간, 삼각부등식 위반, 기간 합집합 템플릿과 일별 계획의 차이는 해당 과제에 관련 있을 때 확인한다. 모르는 업무 의미를 억지로 채우지 않는다.

## intake.json 필드

템플릿의 빈 문자열은 실제 내용으로 채운다. 해당 없음도 이유를 적는다. 다음은 필드 모양이며 실제 과제의 답이 아니다. task.json 스키마는 `.harness/START_HERE_KO.md`를 따른다.

- `schema_version`: 1
- `goal`: 관찰 가능한 결과.
- `sources`: `[{"id":"S1","path":"inputs/brief.md","locator":"요구사항 2","role":"제출 조건 원문"}]`. 실제 파일과 근거 위치. 해시는 도구가 기록한다.
- `components`: `[{"id":"C1","kind":"assignment","decision":"무엇을 결정하는지","inputs":"키/단위 포함","outputs":"후속 전달 값","depends_on":[],"requirement_ids":["R1"]}]`.
- `composition`: 공동/순차/피드백 중 어떤 구조인지와 이유. 독립이면 근거.
- `couplings`: `[{"from":"C1","to":"C2","shared":"공유 자원","handling":"제약 전달·재검증","loss":"분해 시 포기하는 보장"}]`. 양방향 결정 의존은 실행 depends_on에 순환을 만들지 말고 공동 component로 묶거나 피드백 방식을 명시한다.
- `rules`: `[{"id":"K1","type":"hard","source":"S1","meaning":"명확한 규칙","requirement_ids":["R1"],"check_ids":["check1"]}]`. type은 hard, soft, behavior. 모든 task 요구사항을 component와 rule이 덮고 check는 해당 requirement를 실제 참조해야 한다.
- `data_review`: keys, joins, units, time, missing, duplicates, scale를 각각 문자열로. 관찰 명령/결과와 가정 구분.
- `objective`: order, tradeoffs. 사전식은 상위 목표 먼저, 가중합은 서로 상쇄 가능. 업무 동의 없이 대체하지 않는다.
- `delivery`: run_command, submission_method. task.json 실제 deliverables와 일치.
- `baseline`: method, feasibility, check. 단순 해법도 모든 필수 규칙을 만족해야 유효한 fallback.
- `model_size`: estimate, growth_risk, reduction. 변수 수만으로 실행시간을 보장하지 말고 후보의 성장과 전처리 손실도 적는다.
- `unknowns`: `[{"question_id":"Q1","impact":"어떤 결과가 달라지는지","assumption":"미응답 시 중단 범위 또는 임시 가정"}]`. question으로 먼저 등록한 ID만 참조.
- `next_slice`: behavior, check. 작은 입력→결정→독립 검증→실제 출력까지 연결.
- `out_of_scope`: 남긴 한계. 필수 요구를 임의 제외하는 허가가 아니다.

`inputs-reviewed`는 참조/커버리지/실행 순환/실제 source 파일을 검사하고 해시를 보관한다. 자료를 제대로 읽었는지, 제약의 뜻이 맞는지, 모든 숨은 조건을 찾았는지는 자동 판정하지 않는다.

## 질문

현재 답할 수 있는 질문부터 최대 세 개씩 묻는다. “사전식 목적(상위 목표를 먼저 지킴)과 가중합(점수로 서로 교환)이 있습니다. A는 결원 최소화 후 선호, B는 동시 점수화입니다. 결원 허용 여부가 불명확하므로 HR 확인이 필요합니다. 작은 반례로 차이를 확인하겠습니다.”처럼 뜻·선택지·비용·검사를 연결한다. 실행환경처럼 직접 확인할 수 있는 사실은 사용자에게 묻지 않는다.
