---
name: solver-modeling
description: Turn scheduling, routing, allocation or assignment requirements into a solver model and choose OR-Tools, Timefold Community Edition or a simpler baseline using constraints, runtime readiness and measured prototypes. Use before core optimization coding and when material rules change during preparation or AI-permitted work.
---

Read actual requirements, `.harness/work/questions.md`, the supplied environment, and `references/solver-selection.md`. Do not treat scheduling as automatically Timefold or routing as automatically OR-Tools. OR-Tools also handles complex scheduling; both need precise rules.

1. Extract decision variables, fixed facts, units/timezones, IDs, data size, mandatory constraints, preferences and objective priority. Link each rule to a source and an independent acceptance check. Keep assumptions visible. If there is no optimization problem, choose baseline rather than forcing a solver.
2. Compare environment readiness and problem fit. For Timefold 2.x require JDK 21+ and a working local Java build. Do not choose its archived Python port or silently substitute a commercial cloud model API. For OR-Tools select CP-SAT, Routing or another appropriate model explicitly.
3. Draft `.harness/work/model-spec.md` before substantial implementation. For CP-SAT record domains/integer units and variables; for Routing record nodes, vehicles and dimensions. For Timefold record problem facts, planning entities, variables, ranges, solution and hard/soft ConstraintProvider rules. Avoid forcing unrelated tasks into the bundled toy schema.
4. Propose one best candidate with alternatives and switching cost. Ask the user only where business meaning, goal priority or hard-rule relaxation needs their judgment. Record the selected engine using `flow.py select ENGINE --reason ... --alternative ... --evidence ...` if installed. Unrun evidence must be called unrun.
5. Before even a small task-specific solve, fill `.harness/work/spec-review.json` using the runtime guide and run `flow.py review-model --note ...`. Cover every intake rule with its meaning, concrete expected result and boundary result; review objective order, coupled decisions, failure behavior and all blocking decision history. Check the HR inbox first. Every referenced answer must be assessed as clear (or an actual reversible implementation delegation) and reconciled; partial/vague/conflicting replies remain blocked. If sources are unambiguous, record why no HR question is needed; do not invent questions or replies. Environment/version checks and independent scaffolding may proceed while business questions wait. Then run small satisfiable and impossible/boundary cases with explicit inner and outer limits. For any real business algorithm, including baseline, use `flow.py run --purpose solve`; never label it utility to evade review. Run representative full-size input early. Do not build both backends unless evidence warrants it. Bundled adapters are examples, not universal models.
6. Measure model construction, first feasible result if observed, last improvement if observed, solve and independent validation; also measure the whole process. Leave unobserved timestamps null. Track input hash/version, seed, workers, dependency versions and status. Display configured budget and actual elapsed time, never invent ETA from a dataset's row count.
7. Distinguish CP-SAT UNKNOWN from INFEASIBLE and FEASIBLE from OPTIMAL. Preserve Routing's own native statuses. In Timefold a returned candidate can violate hard rules; check assignment completeness and score feasibility plus an independent validator. A heuristic timeout without feasible output does not prove infeasibility or global optimality.
8. Define candidate-result and failure semantics before parallel integration: input version, engine/raw status, candidate presence, feasibility, optimality/infeasibility proof flags, objective/score, timing, validation. Use immutable input snapshots and atomically verify the active version/epoch before publish. Specify fallback exhaustion and stale candidate behavior.
9. Freeze a concrete I/O contract revision; link requirement IDs and acceptance checks. On `contract-ready`, move to bounded build. Revisit the model when a stakeholder answer changes a hard rule or objective. Record decomposition losses and unimplemented guarantees instead of claiming full optimization.

Keep this step focused: identify the right problem and get a measured working baseline quickly. Independently test rules; a solver can optimize an incorrectly modeled problem successfully. Before committing the model, explain what is being decided, what is forbidden, what is improved, one tiny expected result and one unguaranteed property. Record the accepted tradeoff; do not claim the user understood without their response. Check that every decision component in intake has an implementation approach and every shared rule has an independent check. Use the first measured prototype to revise installation/modeling/build time estimates, not just solver runtime. Inspect the HR inbox before a consequential model or contract change.

## v3 coordination

Require the current intake review before selecting an engine and a current model/HR review before each solve. The runtime detects changed sources/specifications/questions, but cannot judge whether natural-language interpretations are true or intercept arbitrary shell commands. Read the component/coupling map: use one solver or a justified staged approach, not one engine by habit. Estimate variables/candidates, record decomposition loss and independently validate shared constraints. If business meaning becomes ambiguous during modeling, use stakeholder-bridge immediately. A material reply returns to modeling and invalidates the contract: re-review inputs and the model before solving, then freeze the updated contract before integration.

Use an inner solver limit below the outer process limit so the adapter can serialize and validate its incumbent. An outer kill may lose that candidate. Set an installation/prototype allowance in the rehearsal; if no working runtime exists, choose the smallest independently validated permitted baseline or disclose the blocker. Do not claim the baseline meets requirements it fails.
