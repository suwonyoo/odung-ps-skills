---
name: task-start
description: Start or resume structured implementation when the user supplies or points to actual task files in this workflow, even without a separate goal, startup prompt or configuration values. Extract requirements from the files and coordinate questions, time and evidence. Exclude toolkit maintenance, reference-only attachments and unrelated small edits; respect actual no-AI rules.
---

Read actual project instructions and files. In this implementation workflow, “문제 자료는 inputs/에 있어” or handing over the actual task brief is sufficient to begin. Do not require a magic start phrase, separately typed desired outputs, a startup questionnaire or explicit skill names. Infer goals, required deliverables, input roles, stack, constraints and time limits from the supplied instructions, then show a short sourced restatement and continue. Ask only about consequential missing/conflicting information after checking accessible files. If attachments are not readable in this environment, state the access gap and request their accessible path. Preserve supplied delivery paths and assessment rules. Opening the toolkit, its bundled examples, a reference-only attachment, a summary-only request or toolkit maintenance does not start a task.

1. Locate the actual task workspace. From the public kit, follow AGENTS.md to install into a separate task directory. Do not copy real task data into the public checkout. If the runtime is absent, say so; do not invent executions.
2. Read `.harness/WORKFLOW_KO.md`. Use the actual remaining time from the user or supplied instructions; if neither provides it, announce a provisional 180-minute work budget without treating it as an official deadline or blocking intake. Preserve an existing clock/state. Do not infer deadlines or HR availability from filenames. After the first file pass, write a rough remaining-work plan and apply `flow.py plan --file ... --reason ...`; refine after intake and the prototype. Use ranges, real dependencies/session capacity, a separate contingency reserve and explicit verification/handoff work. Explain estimates versus measurements; never reset or extend the deadline to make a plan fit.
3. If the user says there is no stakeholder DM, record `flow.py contact --mode none --note 'user wording'` once and retain it across phases and resumptions. Do not ask them to skip DM repeatedly. If they explicitly have a channel, use manual. If unspecified, ask only when an important unknown actually needs it.
4. Follow intake → modeling → parallel-build → integrate → verify → finish. Transition events record readiness; they do not launch skills or agents. Never bypass intake or verification to make the board green.
5. At every phase boundary and new input, inspect hr-inbox.md and unresolved questions, including during build/verification. Re-estimate remaining work after a prototype, material reply, failed check or overrun, and at the plan review interval. Remove optional scope before required behavior or verification; show why the plan changed. Use stakeholder-bridge for material ambiguity. Check local facts first. In no-DM mode use documented facts, reversible AI defaults and necessary user decisions; never invent an external reply or waive a hard requirement. Pause dependent work only where an unsettled decision changes correctness.
6. Publish the first useful finding after the initial file pass; do not stay silent for the whole phase budget. During active work, give a compact update after a meaningful finding, question, changed assumption or result, and aim for no more than about 60 seconds without an update when the client allows it. Use `[i/6 한글 단계 | 현재 작업 | 남은 예산]` then confirmed finding + source, provisional/unknown item, HR change, next action, and `사용자 필수: ... / 선택: ...`; omit empty or unchanged lines. With no required action, say so and offer at most one useful short review of an actual source, sample result or decision. Never invent busywork, HR questions, findings or a timer-driven delivery guarantee. Updates do not require acknowledgment; continue independent work. Explain technical terms plainly. For consequential choices give options, cost, recommendation and one check; never invent an optimality ETA or completion percentage. During a long command, report only observed elapsed time/status until a result exists; yield bounded command waits when supported.
7. Build the smallest input→decision→validation→output slice first. Freeze one I/O/failure contract, assign disjoint files and one owner for shared types/dependencies. Only use parallel agents when authorized and supported. Terminals, AI workers and solver CPU workers are different; never integrate by overwriting directories.
8. Register workers at task start/change/end; wrap expensive commands in timed runs. Keep short actual records using references/working-records.md. Preserve failures and distinguish AI defaults, user decisions, copied replies and actual checks.
9. Protect the plan's remaining verification/handoff allowance plus contingency; freeze optional work when they consume the remaining budget. If no plan exists yet, use 30 minutes only as a provisional fallback. Explain the chosen structure after modeling, real data flow after integration, and evidence/limits after verification in 30–60 seconds each. Offer one concrete consequence question where understanding matters; never mark the user as understanding without an actual response. Verify and hand off exact deliverables. A closed runner does not stop other sessions. Do not automate stakeholder messages or official submission.

On interruption read status and logs; recover only observed dead local processes. Do not turn UNKNOWN into INFEASIBLE or publish an invalid fallback. The runtime checks structure/evidence, while semantic correctness still needs reasoning and real checks.
